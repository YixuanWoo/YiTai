## 1. 四级维护节奏

### 1.1 每次改动必跑门禁（提交前）

- [ ] **看状态、定位条目**：`git status --short`；有未提交改动先弄清归属，到 `docs/TODO.md` 找对应条目（没有就先加条目）。
- [ ] **先复现再改**：在 `tests\YiTai.Tests\Program.cs` 加一条会失败的 `Check(说明, 条件)`；数据类测试一律走 `NewSandbox()` 临时目录，设置类测试必须设 `YITAI_CONFIG_DIR`。
- [ ] **跑门禁**：`.\build.ps1`；通过标准：编译 **0 警告 0 错误**、冒烟测试全部通过、退出码 `0`；警告也算失败。
- [ ] **补文档**：用户可见行为变了 → 更新 README「已知边界」；没做的写进 TODO，不写成承诺。
- [ ] **精确提交**：`git add <具体文件>`，禁止 `git add .`；提交信息带条目号（如 `[T-13] …`）。

### 1.2 每周体检（每次接手的第一次必做）

- [ ] **全量门禁**：`.\build.ps1`；通过标准：0 警告 0 错误；测试项数 ≥ 基线 176 且**只增不减**，退出码 0；删测试必须在 TODO 写明理由。
- [ ] **git 干净度**：`git status --short` 无意外未跟踪文件；`git log --oneline -10` 核对提交信息带条目号；`bin/`、`obj/`、`dist/`、根目录 `YiTai.exe` 均为 `.gitignore` 允许的构建产物。
- [ ] **依赖边界核对**：`Select-String -Path src\*\*.csproj -Pattern "PackageReference"`；通过标准：`YiTai.Core` 无任何 `PackageReference`；`YiTai.App` 只有 `Microsoft.Web.WebView2`。长出新包先按 T-12 的方式写清代价再拍板。
- [ ] **文档一致性**：README「已知边界」与实际行为一致；TODO 勾掉的项都写了验证方式（命令 + 看到的结果）；无过期承诺。
- [ ] **真机冒烟**：打开 `samples\demo`，人工过一遍栏位增减、行号、字数、进度高亮、PDF、GFM 表格、预览（冒烟测试不开窗口，界面回归只能靠人）。

### 1.3 每月体检

- [ ] **Release 演练**：`.\build.ps1 -Release`；通过标准：产出 `dist\YiTai.exe`，根目录 `YiTai.exe` 已同步；两份大小/时间一致（复制失败只警告，需人工确认，不算发布成功）。
- [ ] **数据安全复查**：抽查测试仍落在 `%TEMP%` 沙箱、`YITAI_CONFIG_DIR` 重定向生效；真实 `%APPDATA%\YiTai\settings.json` 的修改时间早于本月跑测；`backups\` 备份链完整、备份名保留原扩展名。
- [ ] **TODO 过期项清理**：勾掉项补验证方式；受阻项（如 T-13 的凭据 scope）更新现状；未做功能不得写成承诺。
- [ ] **大文件抽样压测（T-17）**：在 `%TEMP%` 沙箱造大文档抽样记录输入延迟、行号重建开销、内存占用，数据留档；无真实卡顿反馈不投入增量改造。
- [ ] **风险登记表核对**：`docs/MAINTENANCE.md` 第 6 节「已知坑与风险登记」现状仍成立；过时条目更新，新增风险补登。

### 1.4 每季依赖与安全复查

- [ ] **依赖审计**：列出全部 `PackageReference` 及版本；核对 `Microsoft.Web.WebView2` 是否有安全更新/兼容升级；`YiTai.Core` 保持零第三方依赖。
- [ ] **工具链核对**：`dotnet --version` 核对 SDK 处于 10.0.x 线；跟踪框架补丁与 Breaking Changes；`ci.yml` 中 `dotnet-version: '10.0.x'` 与本地一致。
- [ ] **凭据与隐私扫描**：全仓检索无私人绝对路径、译稿内容、账号/令牌/密码；csproj、脚本、文档中不出现可直接登录的凭据。
- [ ] **发布链路安全**：核对 Release 产物签名状态（T-15 落地后）、Releases 产物来源可追溯、旧版本保留可供回滚。
- [ ] **备份与回滚演练**：从 `backups\` 与改模型前的整目录备份副本，在沙箱里恢复一份项目，验证可回滚；记录恢复步骤是否仍走得通。

## 3. 待办条目规划（T-13 … T-18）

> 现状口径来自 `docs/TODO.md` 第三批与基线报告第 3 节；每条给出目标、步骤、验收、风险、建议优先级与理由。

### T-13 CI 落地

- **目标**：把 `.github/workflows/ci.yml`（restore → build → 冒烟测试，退出码非 0 即失败）纳入版本控制，push 后 Actions 绿勾，让远端也有门禁把关。
- **步骤**：
  1. 核对 `ci.yml` 步骤与本地门禁口径一致（SDK 10.0.x、Debug 构建、冒烟测试退出码判定）。
  2. 解决推送凭据 `workflow` scope：网页 Add file 粘贴，或 `gh auth refresh -s workflow`。
  3. 精确添加：`git add .github/workflows/ci.yml`，提交并推送 `master`。
  4. 观察 Actions 首次运行全绿；顺带核对 `ci-pending` 分支与 `master` 的内容差（基线盘点未核对）。
- **验收**：一次 push 后 Actions 绿勾；远端 `master` 上存在 `ci.yml`；本地 `.\build.ps1` 仍 0 警告 0 错误、测试 ≥176 全过。
- **风险**：token 缺 `workflow` scope 仍推不上去；无桌面环境下 WPF 相关行为无法由 CI 覆盖（当前测试守 Core 与读源码文本断言，不开窗口）；`ci-pending` 遗留差异可能混入旧改动。
- **建议优先级：P1（高）**。理由：本地绿灯不等于远端有门禁；CI 是后续所有改动的兜底防线，越早落地越能防回归；卡点仅是凭据权限，解决成本低，应先于发布自动化。

### T-14 `release.ps1`

- **目标**：把「编译 → 拷根目录 → 打 tag → `gh release create` 挂 exe」串成一条命令，避免手动分步漏步。
- **步骤**：
  1. 封装 `build.ps1 -Release` 的构建与产物同步流程。
  2. 版本号从 csproj `<Version>` 读取，生成 tag `vX.Y.Z`。
  3. 调 `gh release create vX.Y.Z dist\YiTai.exe` 挂产物；脚本内 `$ErrorActionPreference = 'Stop'`，任一步失败即停、退出码非 0。
  4. README 下载链接保持 `latest` 口径，不写死版本号。
- **验收**：一条命令产出新版本 Release；Releases 页挂有对应 exe；README 链接无需手改；重复执行不产生错误 tag。
- **风险**：自动化后漏跑真机回归的概率上升；`gh` 未登录或无仓库权限会失败；脚本版本号与 csproj 不同步。
- **建议优先级：P2（中）**。理由：当前手动分步虽繁琐但可用；待 T-13 CI 落地、发布流程在手动状态下跑稳后再固化成脚本，避免把未把关的链路自动化。

### T-15 exe 代码签名（可选）

- **目标**：减少外部下载者被 SmartScreen 拦「未知发布者」的提示。
- **步骤**：
  1. 自备代码签名证书（pfx）；未备证书前不启动本项。
  2. 发布步骤接入签名（`signtool sign` + 时间戳）；证书与密码不得写进仓库。
  3. 验证签名链与时间戳有效。
- **验收**：`Get-AuthenticodeSignature dist\YiTai.exe` 状态为 `Valid`；安装运行不再报未知发布者。
- **风险**：证书过期/丢失导致签名断档；自签证书仍可能触发 SmartScreen；私钥、口令若进仓库即违反凭据红线。
- **建议优先级：P3（低，可选）**。理由：纯分发体验优化，不影响功能与数据安全；触发条件是有外部下载者实际反馈拦截，且依赖自备证书。

### T-16 检查更新（最小版）

- **目标**：界面提供「帮助 → 检查更新」，仅打开 Releases 页；不做静默下载、不做自替换。
- **步骤**：
  1. 帮助/菜单加入口；点击用默认浏览器打开与 README 同款 Releases URL。
  2. 不接版本号比对、不下载、不自替换。
  3. 补一条冒烟断言（入口存在、URL 正确）。
- **验收**：点击后打开 Releases 页；无后台下载或自替换行为；门禁全过。
- **风险**：最小版只跳页、不告知是否有新版，用户可能困惑；URL 需与 README 保持一致，避免两处硬编码漂移。
- **建议优先级：P3（低）**。理由：功能增量小、价值有限；等 T-14 发布脚本稳定、Release 常态化后再做更顺。

### T-17 大文件性能实测

- **目标**：拿到 50 万字文档连续输入的延迟、行号重建开销与内存占用实测数据，再决定是否需要增量改造。
- **步骤**：
  1. 在 `%TEMP%` 沙箱造 50 万字测试文档（不得落真实项目目录）。
  2. 连续输入，记录输入延迟、行号重建耗时、内存占用与卡顿阈值。
  3. 数据留档；若超标，行号改为「按行增量 + 可见区节流」，并回归全部冒烟测试。
  4. 实测结论写回 README「已知边界」与 TODO。
- **验收**：50 万字连续输入无明显卡顿，且有实测时长/内存数据留档；或已完成增量改造并测试全过。
- **风险**：压测占用机器资源；过早优化增量行号会增加复杂度（当前为已知设计取舍）；测试数据误入真实项目目录即违反数据安全红线。
- **建议优先级：P2（中）**。理由：目前无真实卡顿反馈，但这是已知未验证边界；先在每月体检中抽样压测留数据，出现真实反馈再投入改造。

## 4. 发布与回滚

### 4.1 版本号规则

- 版本号取自 `src\YiTai.App\YiTai.App.csproj` 的 `<Version>`（当前 `0.1.0`），遵循 `MAJOR.MINOR.PATCH`：
  - **PATCH**：边界缺陷修复，不改用户可见行为口径。
  - **MINOR**：向后兼容的新功能 / 新栏位能力。
  - **MAJOR**：数据模型不兼容、界面模型重构等破坏性变更。
- Git tag 格式 `vX.Y.Z`（与 csproj 版本一致）；README 的下载链接按 `latest`，**不写死版本号**。

### 4.2 构建

1. 确认 `master` 工作区干净、本地门禁绿灯（见第 1.1 节）。
2. 发布构建：`.\build.ps1 -Release`
   - 流程：Debug 构建 → 冒烟测试 → `dotnet publish` 自包含单文件（win-x64、`PublishSingleFile`）。
3. 构建退出码非 0 即停止，不得继续发布。

### 4.3 产物与校验

- 产物：`dist\YiTai.exe`（自包含单文件，基线约 59.3 MB）；脚本自动复制一份到仓库根 `YiTai.exe`（日常双击入口）。
- 发布前校验：
  1. `dist\YiTai.exe` 存在、大小与基线量级一致；
  2. 根目录 `YiTai.exe` 已同步，两份大小/修改时间一致（程序运行中复制失败只给警告，须人工确认后才算同步成功）；
  3. 用 `samples\demo` 真机回归：栏位增减、行号、字数、进度高亮、PDF、GFM 表格、预览；
  4. 打 tag `vX.Y.Z`，`gh release create` 挂 `dist\YiTai.exe`（T-14 落地前为手动步骤）。
- 校验和由发布流程/控制面统一处理，本计划不在本地自行计算哈希。

### 4.4 回滚步骤

- **代码回滚**：定位发版对应的 commit / tag；用 `git revert <commit>` 撤销，不使用 force push、不 `reset --hard`；需要回到上一版基线时，基于上一个 tag 重新发版。
- **产物回滚**：Releases 中保留旧版本不删除；将上一版 `YiTai.exe` 重新置顶/重新上传；根目录入口用上一版 `dist` 产物覆盖；新 exe 启动即崩时先恢复根目录入口。
- **数据回滚**：用户项目依赖 `backups\` 每日备份；改动 `project.json` / `.yitai` 前的整目录备份副本用于恢复；进度与栏位布局按备份还原，迁移拿不准的旧键留着等认领，不强行搬。
- **门禁不通过**：不发版；已发版后发现问题，按上述代码/产物/数据三层回滚，并在 `docs/MAINTENANCE.md` 第 6 节风险登记与 TODO 中记录原因。

## 5. 数据安全红线

> 本节是最容易出事的区域，改动前逐条核对；事故背景见 `docs/MAINTENANCE.md` 第 5 节。

1. **`%TEMP%` 沙箱 + `YITAI_CONFIG_DIR`**：测试与临时操作只在 `%TEMP%` 下的沙箱目录（测试用 `NewSandbox()` 建 `%TEMP%\yitai-tests-<guid>`）；设置目录必须经 `YITAI_CONFIG_DIR` 重定向到沙箱内 `config` 目录。**不得**在测试/脚本中直接读写真实 `%APPDATA%\YiTai\settings.json` 或用户项目目录。
2. **改 `project.json` / `.yitai\` 结构前整目录备份**：先把整个项目文件夹复制一份作为备份，保留旧文件读取路径；`Schema` 升版时必须写「旧文件读进来会怎样」的测试；迁移只做有把握的——旧进度键唯一对上才搬，拿不准就留着等认领，宁可重标、不可错标。
3. **备份保留原扩展名**：备份名沿用 `{stem}-工作台-{stamp}{原扩展名}` 规则（T-23），禁止写死 `.md`，避免 `.md` 与 `.txt` 同名时当天备份互相挤掉。
4. **删除可恢复**：删文件走回收站；大件先复制到 `_删除备份\<时间戳>\` 目录再删；**禁止通配符删除**；用户项目可能正被程序占用，落盘前先看 `deliverBlockers`（`YiTai*`）。
5. **凭据与用户数据隔离**：仓库内不写私人绝对路径、译稿内容、账号/令牌/密码；证书私钥与口令不进仓库；真实译稿只在用户自己的项目文件夹，仓库仅保留 `samples\demo`。
